① Root cause: hidden DOM coupling SidebarProvider never imports Popover. It finds any [data-popover] through a document-level pointerover listener, so it reacted to menus it didn't open, like a schedule row's "…" menu.
② Fix: only track while floating A pinned sidebar is always visible, so hidden means nothing there. The listener is attached only when floating, and hoveringPopover resets on a mode switch. Chosen over gating only the close (Option A), which still re-rendered every useSidebar consumer on each popover hover.
③ Close gate kept as a backstop The close effect also requires floating. Without it, switching floating → pinned while a popover is hovered would fire one stray closeContextMenu().
④ One shared menu for the whole app Every context menu goes through one slice and one <ContextMenu>, so closeContextMenu() closes whatever is open. The sidebar can't tell its own menus apart; that floating-mode work is the issue author's follow-up.
⑤ Composition, not just association The provider builds a new SidebarContextValue every render; it can't exist outside the provider. Consumers only reach it through useSidebar().
