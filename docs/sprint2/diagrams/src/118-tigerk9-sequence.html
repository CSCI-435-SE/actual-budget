Issue #118 — Opening a schedule's "…" menu and moving off it — UML Sequence Diagram shows both sidebar modes; the fix is the [pinned] branch
① Opening a menu is an event, not a call The "…" button fires a synthetic contextmenu event on the row, so a right-click and the button share one path through useContextMenu into the shared Redux slice.
② Floating branch unchanged on purpose A floating sidebar still reacts to this unrelated menu and can close it. Fixing that needs the sidebar to know which menus it opened, so it's out of scope (follow-up by the issue author).
③ What broke CI Before the fix this branch ran even when pinned. On CI's slower runner, the 350 ms timer from the first menu fired ~35 ms after the second schedule's menu opened, so the menu vanished and the E2E test timed out waiting for "Post transaction today".
④ The fix: nothing to deliver to When pinned, the effect returns before adding its pointerover listener, so the event never reaches SidebarProvider and hidden never changes. The close effect's floating check is a backstop.
