## Sprint Overview

At the beginning of this sprint, our team met to go over what issues we wanted to close during this sprint, assigned their size and scope through Story Points, and self-assigned to specific issues we wanted to work on. The goal was to complete a minimum of two medium issues each and to review at least two other people's pull requests. While we did not complete every single issue we added to the Sprint 1 Milestone page, each person completed their assigned two issues. Those issues took some more time than expected so no teammates felt equipped to tackle another medium issue during this sprint. Despite not completing every issue we set out to do in the milestone, we learned from this to set more achievable goals for ourselves that are doable in a given sprint rather than trying to fit more than we can handle into a small time-frame.

By the end of the sprint, we delivered CSV and PDF export for a budget month, subcategories on both the main budget page and in reports, a new Personal Goal widget that tracks live spending, an adjustable font size setting, and a floating sidebar that resizes the main content. The icon size setting ([#84](https://github.com/CSCI-435-SE/actual-budget/pull/84)) is still in review and will carry over to Sprint 2.

## Requirements & Design

In all cases, specs were completed before coding started. We made sure to add user stories, acceptance criteria, etc. and update all issues to be more detailed. This made it easier when actually implementing these issues as there was more detail and clear criteria for what the change set out to do. We were surprised at how long it can take to draft up these specific specs for each issue, but we believe it was worth it for the clarity adding specifications to each issue provided. Our PRs this sprint required many more design decisions compared to Sprint 0, as we were working on bigger tasks. For each issue there were many open questions that had to be decided, such as "where should this feature live?" and "what should happen if the user does this?". We also had to make design decisions inside of the codebase. For example, in the codebase there are often many ways to approach one issue and many ways to implement it. We tried our best to write as clean code as possible and look at existing implementations before diving in, to ensure our code remains consistent with the existing codebase.

Some of our key design decisions this sprint:

- **PDF export ([#76](https://github.com/CSCI-435-SE/actual-budget/pull/76)):** We split the original issue and only implemented downloading the PDF, deferring layout polish to a later issue. jsPDF only supports Latin characters by default, so supporting non-Latin currency symbols would have made the PR too large to review well.
- **Shared export logic ([#75](https://github.com/CSCI-435-SE/actual-budget/pull/75)):** CSV and PDF exports use the same data-building module, so both formats always contain the same numbers.
- **Subcategories ([#73](https://github.com/CSCI-435-SE/actual-budget/pull/73)):** Money for a subcategory always comes out of its parent's budget and is capped at what the parent has, rather than coming straight from "To Budget". This keeps totals and "To Budget" correct without changing how the rest of the budget works.
- **Personal Goal widget ([#87](https://github.com/CSCI-435-SE/actual-budget/pull/87)):** We chose a dedicated goal page for full setup, with quick edits available on the card itself, so the card stays simple while still allowing detailed configuration.
- **Floating sidebar ([#79](https://github.com/CSCI-435-SE/actual-budget/pull/79)):** The floating sidebar now shares the same container as the main content, so the page resizes when the sidebar opens instead of the sidebar covering it.

## Test Strategy

For each of the issues implemented, Vitest unit tests were the default. All 13 of our PRs from this sprint included unit tests using Vitest. Isabella's PRs ([#73](https://github.com/CSCI-435-SE/actual-budget/pull/73), [#83](https://github.com/CSCI-435-SE/actual-budget/pull/83)) also included end-to-end tests using Playwright. The other PRs did not include E2E tests, as their changes were small or didn't include a UI component.

Every PR was tested by hand after implementation, both by the person who implemented the issue and the person who reviewed it, with the exception of [#75](https://github.com/CSCI-435-SE/actual-budget/pull/75), which had no UI. Some things that weren't automated include checking how the PDF looks ([#76](https://github.com/CSCI-435-SE/actual-budget/pull/76)), whether settings persist across sessions ([#80](https://github.com/CSCI-435-SE/actual-budget/pull/80), [#84](https://github.com/CSCI-435-SE/actual-budget/pull/84)), and the sidebar layout across various screen sizes. Issue [#70](https://github.com/CSCI-435-SE/actual-budget/issues/70) was supposed to test the layout across various screen sizes but wasn't implemented. One known gap is that `mutations.test.tsx` fails, and this will be addressed in the next sprint.

## Risks & Retrospective

### What went well

- Writing detailed specs (user stories, acceptance criteria, open questions) before coding made implementation much smoother and gave reviewers clear criteria to check against.
- Every PR was reviewed by at least one teammate, and reviewers pulled the changes and tested them locally rather than only reading the code.
- Breaking larger features into dependent issues (PDF export [#60](https://github.com/CSCI-435-SE/actual-budget/issues/60) → [#61](https://github.com/CSCI-435-SE/actual-budget/issues/61), goal widget [#62](https://github.com/CSCI-435-SE/actual-budget/issues/62) → [#63](https://github.com/CSCI-435-SE/actual-budget/issues/63) → [#64](https://github.com/CSCI-435-SE/actual-budget/issues/64)) let us deliver working pieces incrementally.

### What slowed us down

- Medium issues took longer than expected, so no one had time to take on a third issue.
- A miscommunication about which issue we were expected to implement was only noticed after the milestone was created, so a couple of issues were dropped or left open.
- Some test suites fail locally for some team members, which made it harder to tell whether a failure came from our changes.

### What we would do differently in Sprint 2

- Set smaller, more realistic goals for the sprint and leave room for review and fixes.
- Have the person implementing an issue write its spec, so they understand the scope before committing to it.
- Get everyone's local test suite passing early in the sprint so we have a reliable baseline.

### Risks going forward

- At the moment, all tests pass except for 7 tests in the `mutations.test.tsx` file. This is not a critical error, as the app still seems to work as expected, but it is definitely something we should address next sprint so we are error free.
- For the team members whose entire test suite doesn't pass and hasn't passed since we started the project (tests other than `mutations.test.tsx`), we should sit down and figure out why those tests are failing and get them to pass. This could be an issue with Docker or something to do with operating systems, but we shouldn't default to letting tests fail locally; we should all be on the same page where all tests pass.
- The upstream Actual Budget project just released a new update, and we should merge it with our current work.
